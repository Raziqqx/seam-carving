# AI usage declaration

**We used AI tools throughout this project, working with them as a team: for the design,
the implementation, the tests, the benchmarks, the report draft and the slides.** We state
this plainly, as the brief requires. The AI wrote most of the code and the first draft of
this report. The team set the direction, made the decisions, checked what the AI produced
and had it corrected where it was wrong.

**Tools and models.**

| Tool | Model | Role |
|---|---|---|
| Claude Code (Anthropic) | Claude Opus 5.5 | Lead: worked with us to plan the work from the brief and rubric, wrote the requirements checklist, and reviewed the build independently against the rubric |
| Claude Code (Anthropic) | Claude Fable 5.2 | Builder: wrote the code, tests, benchmark scripts, report draft and slides to the agreed plan |

**How we worked with the AI.**

1. *Setting the direction (team).* Before any code was written we decided the approach and
   wrote it into the main prompt (Prompt 1): C++17 with OpenCV used only for image input
   and output and filters; our own Edmonds-Karp, with a library max-flow only as a
   cross-check in a test; a readability rule so that every member can explain every
   function; every number in the report generated by a script; and six milestones that
   match our six presentation sections. The lead model turned this into a checklist that
   maps every item of the brief (1a to 9b) to a file, function or report section.
2. *Building (AI, to the team's plan).* The builder model implemented the library, tests,
   benchmarks, app, CI workflow, this report and the slides. All measured numbers
   (timings, costs, ratios) are generated by scripts in the repository, not typed by the
   model.
3. *Reviewing (AI and team together).* Separate reviewer sessions, which did not see the
   builder's reasoning, graded the result against each rubric row over three rounds,
   re-ran the tests and benchmarks, and listed fixes. We kept a shared decisions log
   (`decisions.md`, passed between members) recording what the AI got right, what it got
   wrong, and what we decided to do about each point.
4. *Team milestones.* The work was split into six milestones, one per member, each on its
   own branch. Each member worked through their milestone in their own AI-assisted
   session (Claude Code driven by a per-member brief, Prompt 4; milestone 3 used Claude on
   claude.ai): building and testing it on their own machine, choosing and committing 2–4
   improvements of their own under their own GitHub account (table below), and being
   walked through the code function by function with practice questions. Milestone 3 was
   merged by its owner through a pull request; the owners of milestones 2, 4, 5 and 6
   pushed their work, and Muhammad Raziq (team lead) merged those branches through pull
   requests that passed CI (and added a formatting fix and the AI-declaration row on
   milestone 2).
5. *Final check.* After all merges we re-ran every test and benchmark, regenerated this
   report and the slides from the merged code, and had several reviewer agents check the
   work in parallel (code and tests, report and analysis, presentation and submission
   requirements), followed by a last review of this report against the rubric and of its
   formatting. Their fixes were applied before submission.

**What the AI got wrong, and how it was caught.** The AI made real mistakes, which is why
every step was reviewed and tested. Examples:

| AI mistake | How it was caught | What was done |
|---|---|---|
| Enlarging an image while recording the animation crashed: the frames were sized for the original image, not the larger one | First review round | Frames are now as large as the bigger of the two sizes; an end-to-end test enlarges with animation |
| The picture of all seams drew later seams at the wrong positions, because removing a seam shifts the columns | First review round | Seams are mapped back to original coordinates with an index map ([3.5](#remove-and-repeat-item-1c)) |
| Timings came from single runs and were too noisy to compare | First review round | Every timing is now the median of 3 runs, with the range shown |
| The report explained the DP's measured growth with cache effects without evidence, and the memory-saving rolling-row DP was slower than the full table | Second review round | The unsupported claim was removed and the rolling version was fixed ([6.4](#improvements-item-5d)) |
| After the milestones were merged, the build without OpenMP failed in CI (warnings about unknown pragmas treated as errors) | CI on `main` | Build setting fixed; CI builds with and without OpenMP |
| The command-line tool accepted `--width 0` and `--width 10abc` | Exact exit-code tests (milestone 4) and the final review | Sizes are now checked and rejected with exit code 1; tests added |
| In the final draft: Table 5 was described wrongly, the bound on the naive recursion's calls was wrong, `best_parent_col` was said to be used by every DP variant, and two section links pointed to the wrong place | Final reviews of the report | Corrected before submission ([2.2](#item-2a-ii-relating-the-problem-to-subproblems), [3.2](#dynamic-programming-item-1b), [6.4](#improvements-item-5d)) |

**What the AI got right, and we kept after checking it.** It noticed that the graph in the
brief, read literally, can never remove a pixel of the last column, and proposed the
one-line fix; we verified both with tests before keeping them ([3.4](#graph-cut-item-4)). It
also derived the tighter growth rate of the number of seams in item 2a-i (from the largest
eigenvalue of a tridiagonal matrix), which we checked against a brute-force count of every
seam ([2.1](#item-2a-i-the-number-of-seams-grows-at-least-exponentially-in-m)). The testing
strategy itself (DP against brute force, graph cut against DP and a library max-flow) was
part of our own plan in Prompt 1.

**Responsibility.** Each member worked through their own milestone and was walked through
its code. The team reviewed the final code and report together, understands them, and
takes full responsibility for the submission.

## Main prompts

**Prompt 1 (main prompt, given to the lead model; abridged, wording kept).**

> You are the lead engineer for my team's Algorithms Assignment 2 (Image Compression by Seam
> Carving). Your goal is a submission that scores "Excellent" on every rubric row and earns
> the full 10 bonus marks, **and** that my team can fully understand before a closed-book
> quiz on it. Work through the five phases below in order. Do not skip any phase or mark it
> done until its exit check passes.
>
> **Inputs.** `Assignment_2.pdf`: the spec. Read all of it, every numbered item 1-9.
> `Rubrics.pdf`: the grading rubric. Team ID 5, six members [names and IDs as on the title
> page]. Language/stack: C++17, CMake, OpenCV 4 (image I/O, Sobel, `imshow`/trackbars,
> `VideoWriter`), Catch2 v3 for tests, OpenMP for the multithreading experiment (5d), Dear
> ImGui + GLFW for the interactive app, GitHub Actions for CI. Small Python + matplotlib
> scripts are allowed only for plotting benchmark CSVs into report figures.
>
> **Hard constraints from the spec.** Third-party libraries are allowed for image I/O,
> gradients/Sobel and math. Do not use any built-in content-aware resizing or seam-carving
> function. Every seam algorithm must be our own code. Implement the max-flow solver
> yourself (Edmonds-Karp, or Dinic if you justify it). A library solver such as Boost Graph
> Library's `edmonds_karp_max_flow` may appear only in a test, as an independent
> cross-check. Every algorithm must support both vertical and horizontal seams.
> Horizontal = run on the transposed image. Recompute the energy map after every seam
> removal, as item 1c requires.
>
> **Readability rule (the quiz depends on this).** Clear names (`cumulative_energy`,
> `backtrack`, `residual_capacity`), short functions, one idea per function. Each core
> function gets a docstring stating its purpose, inputs/outputs, and time/space complexity.
> Add comments that explain *why*. No clever one-liners, no template metaprogramming, no
> unexplained pointer arithmetic or SIMD tricks. If you add an optimised version (OpenMP,
> rolling rows), keep the plain version next to it and test that the two agree. Build with
> `-Wall -Wextra -O2` with zero warnings. Every number in the report (runtimes, seam costs,
> image sizes) must be reproducible from a script in the repo.

> backtracking via a parent table, vertical and horizontal; also a memory-optimised variant.
> Greedy (3): start at the minimum-energy pixel in the first row, then at each next row pick
> the minimum of the <= 3 adjacent pixels. Graph cut (4): build exactly the graph described
> in spec item 4 [...]; run our own Edmonds-Karp, BFS from the source in the residual graph
> to get S, and take the rightmost pixel of S in each row as the seam. Seam insertion.
> Bonus 7a visualisation, 7b interactive app, 7c GitHub Actions. Tests: DP seam cost ==
> brute-force minimum over all seams on many random small grids; **graph-cut seam cost ==
> DP seam cost** on many random grids, and max-flow value == Boost's on the same graph; if
> they ever disagree, investigate the construction and document the finding, do not paper
> over it; greedy valid and cost >= DP, with a hand-built grid where greedy is strictly
> worse; shapes, horizontal == transpose(vertical(transpose)); edge cases; counting check
> for 2a-i. Benchmarks: runtime vs image size and vs number of seams; seam-cost comparison
> and side-by-side visual results on at least 3 test images, compared against plain scaling
